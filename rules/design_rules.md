# webmcp-example 项目设计规范（完整版）

> **版本**：v1.0
> **生效日期**：2026-09-05
> **性质**：低频修订原则 + 高频操作细则
> **适用对象**：所有参与 webmcp-example 研发的设计类任务（Agent 与人员）
> **编制依据**：改编通用设计规范，结合 WebMCP（Web Model Context Protocol）、pnpm + TypeScript monorepo 特性定制；技术栈与领域约定以 `AGENT.md`、`rules/project-rules.md` 为准


## 第一部分：核心原则与红线

### 第一章 总则

#### 1.1 序言
本部分规定 webmcp-example 研发活动中必须遵循的根本原则与不可触碰的红线。所有操作性细节（模板、量化方法、分级规则等）委托给第二部分《操作细则》动态维护，但**不得与本部分任何条款冲突**。

#### 1.2 适用范围
本部分适用于 webmcp-example 的模块架构设计、跨层契约设计（html-app 的 WebMCP 工具接口 / chrome-extension 的发现-执行链路）、新功能开发、工具 schema 变更、配置 Schema 设计、性能优化等所有设计类任务。

涉及**跨层契约（html-app 暴露的 tools 契约、chrome-extension 的注入与执行链路）、工具数据结构（tool 定义 / inputSchema）、浏览器插件切面（manifest / content script）** 的变更，任何情况下不可豁免本部分约束。

- **html-app**：Web 应用 SPA，通过 `document.modelContext.registerTool({ name, description, inputSchema, execute })` 暴露结构化工具。
- **chrome-extension**：浏览器插件，作为 agent 能力层，负责「发现 → 校验 → 执行 → 验证」页面暴露的 WebMCP tools。


### 第二章 核心原则（四支柱）

| 支柱 | 内容 | webmcp-example 语境示例 |
|------|------|--------------------------|
| **原则一：多方案比选** | 每个设计任务必须输出 **≥3 个方案**（上限不超过 5），方案间须有实质性技术差异，禁止伪方案。确因场景限制无法提供 3 个时，须书面说明理由并经用户同意。 | 工具暴露方式三选一：页面直接 `registerTool` vs 通过 `@mcp-b/global`（MCP bridge 提供 prompts/resources）vs 通过 iframe/独立 bundle 隔离暴露；插件发现工具：`getTools()` 轮询 vs `ontoolchange` 事件订阅 vs content script 主动注入 |
| **原则二：多维度评估** | 每个方案必须从**扩展性、稳定性、可维护性、上下游依赖影响、收益评估、成本评估**六个维度进行完整评估，缺失任一维度即视为方案不完整。 | 新增工具时须评估：`inputSchema` 演化兼容性、执行函数异常边界、polyfill / MCP bridge 版本兼容、对 chrome-extension 侧校验参数的影响、卸载/页面销毁回收成本 |
| **原则三：确认后执行** | 方案未经用户明确确认，禁止开始执行。确认后须复述方案要点，确保理解一致。模糊回复（如"再看看""继续"）不视为确认。 | 遵循先设计后实现：给出方案与评估 → 用户明确确认 → 复述关键契约 → 进入实现 |
| **原则四：禁止静默变更** | 执行中遇方案缺陷、环境不符、新需求、未覆盖边界等情况，必须立即停止，走变更确认流程，禁止擅自修改后继续执行。 | 如工具 `execute` 返回契约因 `@mcp-b/*` 升级而签名变化，必须停止并按 L3 流程重新评估，禁止直接改代码绕过 |

> **跨层契约前置核对**：涉及 html-app 的工具暴露接口（`inputSchema` / `execute` 返回）、chrome-extension 的注入与执行链路（manifest / content script / MCP Client）改动，必须先查阅 `git-source/npm-packages/AGENTS.md` 与 WebMCP 草案（`docs/webmcp.md`）核对当前 API 形态，并对照 `git-source/` 内上游源码实证，禁止凭记忆假设契约。


### 第三章 禁止事项（红线清单）

| 编号 | 禁止行为 |
|------|----------|
| **P1** | 未提供 3 个实质性方案即要求确认或开始执行 |
| **P2** | 输出仅有名称或参数不同的伪方案 |
| **P3** | 未分析优缺点、收益及成本即输出方案 |
| **P4** | 将用户模糊回复视为确认并开始执行 |
| **P5** | 执行中修改方案后**静默继续**，未走变更流程 |
| **P6** | 变更方案未经完整评估即重新执行（分级标准见第二部分） |
| **P7** | 用户提出矛盾需求时，不停止澄清、擅自选择一侧推进 |
| **P8** | 修改上游参考仓库（`git-source/*` 子模块）、`node_modules` 或第三方包里的任何内容 |
| **P9** | 涉及跨层契约（html-app 工具契约 / chrome-extension 注入与执行链路）的改动，未先查阅 `docs/webmcp.md` 与上游核对文档即实施 |
| **P10** | 涉及工具 schema（`inputSchema`）、执行返回数据结构的改动，未先告知用户 |
| **P11** | chrome-extension 绕过 WebMCP 暴露接口（`getTools` / `executeTool` / MCP Client），直接访问 html-app 内部模块或数据源 |
| **P12** | chrome-extension 的 content script 未经锚点隔离，触碰自身注入区域之外的页面 DOM 或宿主特权作用域 |
| **P13** | 敏感凭证（API Key、Token、数据库连接串等）硬编码进代码或配置 |

> P8 ~ P13 为项目专属红线，源自 `AGENT.md` 与 `rules/issues_rules.md` 的安全与合规要求，优先级与 P1 ~ P7 相同。


### 第四章 豁免与例外

- **可豁免多方案流程**（但须遵守其他原则）：单行修复类微调（改文案、改 CSS 值、改明显笔误）；用户已书面指定唯一实现方式的任务。
- **不可豁免**：任何涉及**跨层契约（工具契约 / 注入与执行链路）、工具数据结构（tool 定义 / inputSchema）、配置 Schema 结构性变更**的改动，即便用户要求简化，也必须走完整流程。


### 第五章 第一部分与第二部分的关系

- 第二部分《操作细则》是本部分的实施细则，可随项目演进迭代更新。
- 第二部分中的任何条款不得与本部分冲突。若冲突，以本部分为准。
- 本部分的修订须记录版本历史及修订理由，且须经过与制定时同等层级的评审。


## 第二部分：操作细则

### 第六章 方案输出细则

#### 6.1 数量与质量
- 最少 3 个方案，**最多 5 个方案**（防止选择瘫痪）。
- **"实质性差异"在 webmcp-example 语境下指在以下层面存在本质不同**：
  - **工具暴露方式**：页面内 `document.modelContext.registerTool` 直接注册 vs `@mcp-b/global` 全量 MCP bridge vs 仅 `@mcp-b/webmcp-polyfill` 核心极简暴露
  - **工具接入形态**：直接调用 `execute` 回调 vs 经 React hooks（`usewebmcp` / `@mcp-b/react-webmcp`）vs iframe 隔离 bundle
  - **插件发现链路**：`getTools()` 主动轮询 vs `ontoolchange` 事件驱动 vs content script 主动 push
  - **执行与校验**：插件侧按 `inputSchema` 强类型校验后调用 vs 页面侧 `execute` 内部自校验 vs JSON Schema 校验库统一校验
- 仅修改变量命名、颜色值或注释内容视为无效方案。
- 若确因场景限制无法提供 3 个方案，须在方案开头明确说明限制原因，并经用户书面同意。

#### 6.2 评估维度详解（统一口径，webmcp-example 示例）

| 维度 | 评估要点 | 评级与量化标准参考（webmcp-example 语境） |
|------|----------|--------------------------------------------|
| **扩展性** | 新增工具、新增插件能力、新页面接入成本；`inputSchema` 演化是否顺畅；新工具是否仅通过 `registerTool` 追加而无需改动既有模块 | **高**：新增工具仅需追加一次 `registerTool` / 插件仅新增执行分支，无需修改既有契约；**中**：需少量适配（新增配置项、扩展事件、加依赖）；**低**：需重构工具注册编排或插件注入结构 |
| **稳定性** | 事件/订阅生命周期托管、插件卸载与页面销毁自动回收、`execute` 异常边界、polyfill / MCP bridge 版本兼容、无原生支持时的降级 | **高**：定时器/订阅/监听全部托管，卸载自动回收；`execute` 纯逻辑、无关输入返回稳定结果；有降级与回滚预案；**中**：有常规 try-catch 但无降级；**低**：关键流程无容错、事件处理含副作用、依赖版本兼容性未知 |
| **可维护性** | 模块按功能点拆分（单文件 ≤800 行）、TypeScript 强类型（禁止 `any`）、注释四层结构、测试覆盖率、圈复杂度 | **高**：逻辑清晰，模块职责单一（如 tool-defs / register / extension / verify 分文件），单元测试易写；**低**：大量副作用、深层嵌套、难以调试 |
| **上下游依赖影响** | **上游（方案依赖方）**：`@mcp-b/*` 依赖、WebMCP 草案演进（`executeTool` 入参形态）、pnpm 工作区共享类型。**下游（方案影响方）**：工具契约/`inputSchema` 变化对 chrome-extension 校验与执行的影响、公共类型/工具函数被引用后的连锁反应 | **低影响**：无新增上游依赖；影响仅限当前模块内部，无跨包引用扩散<br>**中影响**：需升级 1~2 个 `@mcp-b/*` 补丁版本，或修改少量公共类型，影响限于 html-app 或 chrome-extension 单侧<br>**高影响**：依赖 WebMCP 草案 API 破坏性变更；修改跨层契约（工具 schema / 执行链路 / manifest），需协调 html-app + chrome-extension 双侧回归验证 |
| **收益评估** | 从 4 个子维度综合评定：**扩展收益**、**稳定收益**、**可维护收益**、**异常场景覆盖收益**（边界：原生不支持、polyfill 未加载、插件卸载、工具缺失、版本差异） | 收益尽量量化（如"接入新工具耗时预计减少 50%"、"校验失败提前到插件侧，无效调用下降 60%"、"异常识别从延迟几分钟降至即时"）；难以量化时提供可观测改善迹象 |
| **成本评估** | 从 4 个子维度综合评定：**影响范围**（波及的模块数、跨层契约数、下游依赖数量）、**异常场景代价**（工具契约变化、插件加载失败时的回滚复杂度）、**开发成本**（开发 + 自测 + 联调 + 兼容性验证人天）、**维护成本**（文档维护、依赖升级适配、技术债务偿还） | 成本统一以**人天**为单位（1 人天 = 8 小时有效工作），须明确子项拆分（如"开发 3 人天 + 自测 1 人天 + 契约联调 1 人天"） |

#### 6.4 输出模板（分级使用）

- **标准方案（≥3 个）**：包含优缺点、六维评估详细评级表、对比总表、推荐意见。
- **轻量方案（仅限豁免场景）**：仅需输出核心思路（200 字内）+ 理由说明 + 风险提示，无需完整六维评级。


### 第七章 确认与执行流程

#### 7.1 明确确认规则
- **视为"明确确认"的关键词列表**（白名单）：
  - "选择方案 X / 选第 N 个"
  - "同意 / 确认 / 可以 / 开始执行"
  - "按方案 X 执行"
- **视为"未确认"的模糊回复**：
  - "再看看""继续""稍等""行吧"（无明确指向）
  - 仅提出疑问但不附带确认意向
  - 超过 **48 小时**无回复（超时条款）
- **超时处理**：用户 48 小时未确认，Agent 须发送一次催办提醒；若再经过 24 小时（累计 72 小时）仍无明确回复，则该设计任务**自动挂起**，Agent 停止推进并归档当前方案，待用户重新激活。

#### 7.2 确认后动作
Agent 须复述所选方案的核心技术路线、关键假设和主要风险（如"采用 html-app 引入 `@mcp-b/global` registerTool 暴露 + chrome-extension 用 `ontoolchange` 事件驱动发现 + 插件侧按 inputSchema 校验，兼容无原生支持浏览器，风险在于 `executeTool` 入参形态随 WebMCP 草案演进需按目标版本核对"），用户回复"确认无误"后方可进入执行阶段。若用户发现复述有偏差，须回到方案调整阶段。

#### 7.3 变更流程（三级分级处理，webmcp-example 场景示例）

| 变更等级 | 适用情形（webmcp-example 示例） | 处理要求 |
|----------|--------------------------|----------|
| **L3（重大变更）** | 修改跨层契约（html-app 工具的 `inputSchema` / `execute` 返回契约；chrome-extension 的 manifest / content script 注入 / MCP Client 链路）；工具结构或类型定义变更；配置 Schema 结构性变更 | 按第六章 6.4 完整模板重新输出修正方案，等待用户确认 |
| **L2（一般变更）** | 新增工具（复用既有 schema 模式）；调整工具 `description`/`execute` 内部逻辑；调整插件发现策略参数（轮询频率、事件过滤）；新增 `@mcp-b/*` 依赖；调整配置默认值 | 输出**简化变更说明**（变更原因 + 原/新差异对比 + 影响范围），等待用户确认 |
| **L1（轻微调整）** | 修改 CSS 样式值；调整文案；添加调试日志；更新依赖补丁版本 | **执行后**在进度汇报中主动说明偏差及原因，无需提前等待确认，但必须记录 |

> ⚠️ 任何变更均**禁止静默执行**（L1 可执行后报备，但不得隐瞒）。

#### 7.4 矛盾需求处理
若用户在不同节点提出相互矛盾的要求，Agent 必须：
1. **立即停止**当前推进；
2. 列出矛盾点清单，以表格形式呈现冲突内容；
3. 请用户明确优先级排序，或给出取舍原则；
4. 用户澄清后，按新的优先级重新评估或选择方案。


### 第八章 评估量化指引（webmcp-example 专属指标）

- **成本量化**：必须使用统一单位 **"人天"**（1 人天 = 1 人有效工作 8 小时）。按以下子项拆分明细：
  - 开发人天（代码编写）
  - 自测人天（单元测试、功能自测，如工具 `execute` 与 schema 校验测试）
  - 联调人天（html-app ↔ chrome-extension 契约联调、WebMCP 工具推帧 / 执行验证）
  - 兼容性验证人天（目标 `@mcp-b/*` 版本、无原生支持浏览器行为验证）
  - 文档更新人天

- **收益量化**：优先使用以下 webmcp-example 可观测指标（若适用）：
  - **扩展性收益**：新增同类工具 / 新场景的预估耗时变化
  - **稳定性收益**：工具暴露成功率、插件执行成功率、异常识别时效提升
  - **可维护性收益**：代码圈复杂度预计降低幅度、测试覆盖率提升幅度
  - **异常场景覆盖收益**：边界场景覆盖数量增加（原生不支持、polyfill 未加载、插件卸载、工具缺失、版本差异）、无效工具调用下降比例（插件侧 schema 前置校验收益）

- **上下游依赖影响量化**（结合定性 + 定量评估）：
  - **上游依赖风险**：需新增/升级的 `@mcp-b/*` 包数量、WebMCP 草案改动跨度、上游维护活跃度与破坏性变更预告
  - **下游扩散范围**：直接修改的模块数量、被该模块间接引用的插件/页面模块总数
  - **连锁反应预判**：修改是否触及工具 schema、跨层契约等易产生广泛影响的部分
  - **兼容性扩散**：是否因升级依赖导致 html-app 与 chrome-extension 双侧需同步调整

- **若收益确实无法量化**（如"提升代码可读性"），须定性说明**预期可观测的改善迹象**，并给出验证方法（如 Code Review 评分、单元测试覆盖率）。


### 第九章 执行过程规范

1. 严格按确认后的方案执行，不擅自增删功能或调整范围（如不额外引入未提及的第三方库）。
2. 属文件变更的任务必须写明**变更文件路径**与**完整变更内容**（以 diff 新增/删除/修改行形式呈现），禁止只写文件路径而无 diff 片段。
3. 复杂方案须**分步执行**，每完成一个关键里程碑（如"通过 typecheck""通过单元测试"）向用户汇报进度。
4. **逐个完成**：按任务清单顺序逐个完成，每完成一个立即勾选，禁止跳步或批量勾选。
5. **变更聚焦**：每个任务只做该任务要求的最小、聚焦改动，避免无关重构与过度设计。
6. 若执行细节与方案存在轻微出入（且未达到 L2/L3 变更标准），在当次进度汇报中**主动说明偏差及原因**。
7. 遇阻断性问题（如目标版本无该 API、依赖版本冲突、契约与文档不符），立即停止并汇报，不自作主张改道。
8. **自主解决**：遇到阻塞问题优先尝试自主解决，仅在无法解决时才向用户提问；执行已确认任务时禁止不必要的提问，须完整执行所有任务（含单元测试、验证等收尾任务）。
9. 完成后汇报：执行完成后一次性汇报全部任务完成情况，不中途汇报进度；保持最小消耗（最少调用、最低消耗）。

#### 附录 D：项目代码风格与安全合规速查（源自 AGENT.md / rules/*）

| 类别 | 要求 |
|------|------|
